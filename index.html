Agent execution framework

Loops and Graphs

AI agents write code fast, but they still need you to check every step. This framework fixes that. You write the checklist once. Every task must pass a real check before it moves on. Independent tasks run in parallel. You approve the final merge.

Three pieces make it work. A check replaces your eyes. A graph replaces your judgment about order. A gate replaces your approval at every step. What is left for you is the final merge.

That is harness engineering. Every agent system has one. This one is written down.

You check every step your agent takes. Not because you want to. Because if you do not, mistakes get through. This framework moves that checking into the system.

Most loops are not loops

In August, researchers from Heidelberg and Singapore Management University searched 36,487 maintained repositories for agents running in autonomous loops. They confirmed 217.

Nearly all of them had the trigger. After that, the numbers fall off a cliff.

  • 101 had a spending or turn limit.
  • 76 had a verifier.
  • 55 had a goal or stop rule.
  • 35 kept state between runs.
  • 10 recorded what it cost.

One triage loop logged 6,290 runs. In every run the researchers checked, the agent never fired. A trigger is not a loop. It is a cron job with your credit card attached.

The study found no systematic evidence for the promised 10x yet. This framework does not promise one either. The parts everyone skips, the check, the state, the gate, are the parts that decide whether a loop is worth running. Source.

A loop checks its own work

A loop is a job that checks its own work and fixes itself when it is wrong. Like a student with an answer key. No teacher needed.

Four steps:

  1. Do the work. Write the code, run the search, build the report.
  2. Check it. Against something that can say no.
  3. Fix what the check caught.
  4. Repeat until it passes. Cap at three tries.

The check is the whole point. If it cannot fail, it is not checking. Tests pass. Type checker reports zero errors. Those are checks. "Looks right," "model is confident," "no errors raised": not checks.

A loop with a real check runs while you are somewhere else. A loop without one repeats the same mistake until it runs out of money, with a clean log.

One loop cannot see the whole job

A loop makes one job correct. It cannot decide which jobs exist or what order to run them. An agent can write five perfect functions in the wrong order, or run step four while step three waits for nothing. Every loop did its job. The plan did not.

The graph is the layer above

The graph holds that wider view. It is the shape of the work: what runs, what runs in parallel, what waits, where results go back. Two things: nodes and edges.

A node is one job: one input, one output, one owner. An edge is a real dependency: the next step reads the previous step's output. If nothing crosses, there is no edge. The steps can run at the same time.

A planned graph is that map drawn before work starts. You draw it so the agent does not invent the structure while doing the work.

Treating "and then" as an edge is the mistake behind every unnecessary wait. Summarize the file and then check the weather. No edge. The weather does not read the summary. A linear script chained them because of the order you typed them.

Test every arrow in a pipeline you already have: does the next step actually read the previous step's output? If you cannot name what crosses, there is no edge. The wait is waste.

Four kinds of node

TypeRoleExample
SplitterCuts the work into units and writes each brief.Divide a refactor into slices by blast radius.
WorkerDoes one unit with one lens, in its own context.Audit one slice for race conditions.
Code nodeApplies a transformation with one correct answer.Merge, rank, deduplicate, compare exports.
GateDecides whether a unit's output may continue.Open only if tests pass and scope is clean.

The code node is the one people forget. Merging, ranking, deduplicating: one correct answer, a few lines of code. A model adds cost, latency, and variance to a step that had none.

If you can describe it without saying judge, decide, assess, or summarize, it is code.

Where the loop actually lives

The loop lives inside a node. The graph lives between them.

Inside one unit: produce, check, correct. Between units: split, fan out, merge, gate, send back.

You do not choose between them. A graph without loops makes unverified work in parallel. A loop without a graph is one good step in a queue nobody designed.

The two return paths

A graph without a way back is a pipeline. It produces output and forgets.

Two return paths, two jobs. A correction edge rejects one unit back to the step that made it. Fixes this run. A learning edge sends an accepted result back to the splitter as a constraint. Fixes every run after.

Almost everyone builds the first. The tell is a system that is fast and never gets smarter.

The learning edge does not carry the output, it carries a constraint derived from it. Accepted: utils slice ported, green on first pass. Derived: adapters preserve keyword args exactly. Lands in: the splitter's brief for every later slice.

Return the unit, not the batch

Four slices ported. One fails. Send the whole batch back and three correct slices get rewritten into different, not better, versions. Now you re-verify all four. One failure became four uncertain outcomes.

Every return carries five things:

  • UNIT — handlers slice.
  • VERDICT — red.
  • REASON — test_auth_redirect failed.
  • EVIDENCE — expected 302, got 200, handlers/auth.py:88.
  • SCOPE — fix this file only, do not touch other slices.

The scope line matters most. Without it a returned unit grows: the agent notices two adjacent issues, fixes those too, and your one-slice correction becomes a four-file diff nobody reviewed.

Open the gate on blast radius, not on confidence

Most systems gate on a confidence score. Wrong variable. Confidence is the only input the model can influence.

LaneReversibilityGate rule
Open firstReversible and containedCopy changes, tests, isolated functions with coverage. One bad merge costs a revert.
Open secondReversible but wideShared utilities, schema additions, anything a dozen callers touch. Gate on deterministic checks plus a clean trajectory.
Never openHard to reverseMigrations, deletions, anything writing to production data or moving money. This lane does not open, regardless of score.

The third row is not a high threshold. It is a closed lane. Thresholds get adjusted. Closed lanes do not.

Where to start

Pick one thing you do repeatedly. Draw the splitter, the lanes, the merge, one gate, one back edge.

Build the gate first. A graph without a gate is a faster way to produce unverified output. Then the lanes. Then the learning edge, because you cannot learn from accepted results until something accepts them.

Put the human on one step: the merge. Approve it. Nothing else.

Three lines hold the whole discipline

  • Measure the path, not only the answer it landed on.
  • A verdict that does not change what runs next is a report.
  • Any failure you do not turn into a permanent constraint, you will meet again.

Most people tune one loop and call it a system. The ones who draw the graph around it run a fleet.
